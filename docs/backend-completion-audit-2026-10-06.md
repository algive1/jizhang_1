## 结论与边界

现有服务已承载真实业务协议，适合继续增量完善。需要把现有会员、支付、AI、版本和运维能力纳入统一控制台，并补齐 APP 消费配置、真实供应商接入和业务异常处理。管理页面、接口实现、客户端接入、供应商实测分别验收。

当前存在两套管理入口：新控制台使用独立管理员与角色权限；旧 `/admin` 和部分策略接口使用管理 Token。会员配置、人工开通、消费洞察策略及客服回复仍有能力停留在旧入口。后续复用原业务服务和数据表，统一管理员权限与审计。

APP 版本发布负责“用户安装哪个版本”；后端服务更新负责“服务器运行哪个程序版本及数据库迁移”。两者分别管理。

## 优先解决的具体问题

### 1. 支付结果确认和退款闭环

`payment.ts` 的订单详情接口只读取本地订单，没有向微信/支付宝查询交易。APP 调起 SDK 后仅立即刷新、再延迟两秒刷新会员与记录。因此支付通知漏达或延迟时，存在用户已经付款但权益未更新的情况。需要 APP 回到前台按原订单确认、服务端主动查单和补偿任务，并明确待支付/已支付/关闭/退款中的展示。

代码虽有 `refunded` 状态枚举，未实现微信/支付宝退款请求、退款查询、退款通知和权益调整。新增退款应记录原因、操作者、渠道退款号及状态，同一退款请求幂等；会员权益处理应依据已确定的退款规则，不能只修改订单文字状态。

现有回调已验签和校验金额，仍需补齐微信应用/商户/币种和订单渠道、支付宝卖家和订单渠道校验，微信下单响应验签与公钥/证书轮换，以及乱序通知的状态约束。

参考：[微信支付回调与查单指引](https://pay.wechatpay.cn/doc/v3/merchant/4012075249)、[微信 APIv3 签名验签](https://pay.wechatpay.cn/doc/v3/merchant/4012365342)。

### 2. 会员配置应真正控制权益和额度

当前会员等级只有 `pro/family`，套餐周期只有 1/3/12 个月。套餐覆盖中的 `value` 用于展示文字，并非结构化次数或存储容量；AI 使用次数仍由助手策略的统一 `memberDailyLimit` 提供。需要定义功能开关、AI 调用数、ASR 次数或时长、云容量等实际执行的字段，只有业务确实需要的额度才新增。

助手的会员资格还会读取旧 `assistant_memberships`，并以 `automaticBookkeeping` 权益判断资格；语音客户端则以 `voiceAi` 权益判断。需要统一权益来源，按实际请求功能校验，避免套餐单独关闭某项功能后前后端判断不一致。

新后台用户列表通过多个来源的到期时间做 OR 判断；实际会员接口优先处理人工取消。由静态逻辑可见，人工取消覆盖一个尚未到期的订阅时，列表可能仍标为会员。列表筛选、用户详情、APP 和接口鉴权应遵守同一优先级。

如销售家庭共享会员，应定义享受权益的成员、人数及解绑规则；当前 `family` 等级标签本身不足以说明这些行为。升级/降级时剩余有效期如何处理也需要明确，不能简单把不同等级的剩余时长全部叠加。

### 3. 付费限制仍被测试开关覆盖

`lib/core/config/testing_access.dart` 的 `ALL_FEATURES_FREE_FOR_TESTING` 默认值为 `true`；`server/.env.example` 也设置为 `true`。正式包和正式服务必须使用明确的发布配置关闭该开关，并验证免费/有效/到期/人工取消账号的行为。本轮保持现有测试环境设置。

### 4. 模型管理仍有场景与协议边界

目前所有场景选用同一个最高优先级模型，场景影响 Prompt 和统计；`provider` 字段只是配置标签，实际均发送 `/chat/completions` 请求。优先接入 DeepSeek 和其他 OpenAI 兼容供应商；其他协议在确定供应商后增加适配。

密钥仍由服务端环境引用提供。后台应管理非敏感参数、配置信息与连接检测；若需要后台直接录入密钥，则增加服务端加密保存、覆盖更新和轮换，页面不回显完整值。Token 缺失时费用维持未知；已有费用是按配置单价的估算，后续如使用缓存/推理等不同计价需保留供应商实际 usage 字段。

默认模型 ID 和可选参数应在联调时依据实时模型清单验证，不能沿用历史 ID 就宣称接通。参考：[DeepSeek 官方接入说明](https://api-docs.deepseek.com/zh-cn/)。

### 5. ASR 必须同时改 APP 和后端

现有 `speech_to_text` 返回设备识别文本，没有可直接提交给腾讯的录音文件。建议沿现有 `SpeechRecognitionService` 增加云服务实现，APP 录音后提交给自己的后端，再调用腾讯 `SentenceRecognition`，返回文本后复用规则解析与 AI 解析。

腾讯接口用于不超过 60 秒的短音频；数据大小上限为 3MB，使用 Data 模式时应按文档约束校验 Base64 后的大小。配置引擎、音频格式和热词；服务端处理腾讯签名、用户鉴权、额度、幂等及超时。后台统计请求数、时长、耗时和受控错误码，原始录音与识别正文不进入常规日志。参考：[腾讯一句话识别官方文档](https://cloud.tencent.com/document/product/1093/35646)。

### 6. 灰度发布和同版本构建更新尚未闭环

APP `/app/update` 请求只传 `platform/version`，没有 `installationId`，现有服务因此只向它返回全量发布。需要复用稳定安装标识。

APP 已读取 build，但未提交；更新判定只比较版本名。相同版本名的不同构建不能被识别为更新。应在兼容原客户端协议的前提下引入 build/versionCode，并记录渠道和平台。现有“发布版本”仅发布更新策略，尚不会上传或构建安装包。

### 7. 默认容器交付存在启动缺口

`server/Dockerfile` 仅复制编译产物和脚本，没有复制 `assets/config/membership_catalog.json` 与 `assistant_policy.json`；启动注册会员/助手时会查找并读取这些文件。Compose 未挂载它们。静态检查表明当前默认镜像缺少启动必需资料；尚未在本机运行容器复现。

`server/docker-compose.production.yml` 与 `admin-web/compose.yaml` 各自创建 app/API 和数据卷。若分别按默认 Compose 项目运行，会形成两套服务与数据库。正式交付需要让 APP API 与后台 API 指向同一业务实例和数据库。

基础 CI 已检查服务端类型和测试，尚需纳入新后台 lint/typecheck/build/浏览器测试、镜像启动、迁移兼容及发布任务。后端更新由受控发布任务处理指定版本产物，记录备份、迁移、健康检查和失败回退，避免在网页中执行任意终端命令。
