# 票据 OCR 接入边界

## 当前状态

- Flutter 已能选择图片并保存到应用私有目录，现有附件记录可关联到流水。
- 交易模型已有 `TransactionSource.ocr`，规则解析器已有结构化交易校验能力。
- 助手图片按钮目前只提示“图片记账识别开发中”，没有上传图片、调用 OCR 或自动落库。

## 推荐链路

1. 用户选择或拍摄票据，客户端检查图片格式、大小和会员权限。
2. 客户端通过 HTTPS 将图片交给后端 OCR 接口；API key 只存在后端环境变量。
3. 后端调用指定 OCR/视觉 Provider，返回结构化候选：金额、币种、商户、时间、支付方式、明细和置信度，同时保留原始 OCR 文本用于纠错。
4. 客户端展示可编辑确认卡片。账户、分类、金额或时间不唯一时必须让用户补充，不能自动猜测。
5. 用户确认后复用 `QuickBookkeepingService` 真实落库，流水来源写为 `ocr`；只有落库成功才显示成功状态。

## 待确认接口形态

推荐先实现 `POST /api/v1/assistant/ocr`，请求包含 `requestId`、`contentType` 和图片内容（或后端对象存储引用），响应包含：

```json
{
  "requestId": "...",
  "source": "ocr",
  "candidates": [
    {
      "type": "expense",
      "amount": 12.0,
      "currency": "CNY",
      "merchant": "示例商户",
      "occurredAt": "2026-09-13T12:25:00+08:00",
      "accountHint": "微信支付",
      "categoryHint": "餐饮",
      "confidence": 0.92
    }
  ],
  "rawText": "..."
}
```

Provider 需要实现独立的 `ReceiptOcrProvider` 抽象。后端策略层负责鉴权、会员、每日次数、图片大小和幂等；Provider 负责具体 OCR 协议。OCR 结果永远只是候选数据，不能绕过客户端确认和业务落库。

## 开发所需资料

- OCR 方案：设备端 OCR，云 OCR，还是支持视觉输入的 DeepSeek/第三方中转模型。若使用现有中转站，请提供其图片请求格式、模型名、接口地址和返回示例；key 继续放服务端环境变量，不要写入代码。
- 票据范围：普通小票、发票、支付截图、银行卡账单等，以及是否允许一张图识别多笔流水。
- 字段规则：是否需要税额、发票号、门店、商品明细；币种和外币是否第一阶段支持。
- 会员规则：OCR 是否仅会员可用、免费次数、会员次数、单张图片大小和每日图片张数。
- 数据策略：原图是否只保存在本机、是否上传后端、保留多久、是否允许用于 Provider 处理后立即删除。
- 联调样本：3～5 张已脱敏的真实票据图片和期望识别结果，覆盖金额、时间、支付方式不清晰的情况。

收到这些资料后，才能实现真实 Provider 和联调；在此之前不会用固定文本或假返回冒充 OCR。
